# 扩展如何工作

本页解释首期扩展模型。方法签名、字段和错误说明见 [API 参考](api.md)，具体 manifest 和提案格式见 [扩展接口](extensions.md)。

## 谁负责什么

```text
BORING 设备
    ↓ 实体触发
BORING Console / Community
    ↓ 本地扩展接口
你的 Python 扩展
    ↓
你定义的电脑端动作
```

控制台负责连接设备、读取事件、管理扩展和配置事务。扩展负责自己的动作逻辑，通过 SDK 与控制台交流，不需要自行处理串口通信。

扩展在电脑上运行；离开控制台和扩展运行进程，电脑端自定义动作不会自动转移到设备里执行。

## 观察事件

观察者收到事件副本，用于查看触发、记录日志或了解事件内容。它不会因为收到事件就阻止原来的提示词粘贴。

首期语义事件是 `prompt.triggered`，表示设备的提示词槽位被触发。它不能被当成普通按键、旋钮或摇杆原始输入事件。

适合先用观察示例判断“设备触发有没有到达扩展”。

## 处理绑定动作

如果希望触发时执行自己的逻辑，需要声明扩展动作，并由用户在控制台将具体设备的提示词槽位绑定到该动作。仅导入或启用扩展，不代表它已经接管任何实体触发。

当前设计的处理顺序为：

```text
内置本地自动化 → 已绑定且就绪的扩展动作 → 提示词粘贴回退
```

扩展动作未就绪、拒绝或未及时接受时，控制台按既有流程回退。动作已经接受后再执行失败，不会因此重复粘贴或重复执行。具体时限以发布版本为准。

一个动作可能依次经历“已接到调用”“已接受”“已完成”或“失败”。显示扩展正在运行，只证明进程存在，不代表实体触发已绑定，也不代表动作已完成。

## 提交按键映射提案

扩展可以提出按键映射建议，由控制台展示给用户审阅。

```text
扩展提出建议 → 用户批准到本地草稿 → 用户确认写入 → 设备读回
```

批准提案并不等于已经写入设备。设备或配置发生变化时，旧建议可能失效，需要基于当前状态重新提出。

## 三类示例的阅读顺序

| 示例类型 | 先理解的事情 |
|---|---|
| 观察事件 | 真实设备触发如何到达扩展 |
| 处理绑定动作 | 如何接受调用并报告结果 |
| 映射提案 | 如何向用户提出配置建议 |

三个示例已发布，见 [示例说明](../examples/README.md)。先运行原始示例，再修改自己的动作，有助于区分环境问题与自定义逻辑问题。
