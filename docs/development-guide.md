# 从示例到自己的扩展

本次提供 SDK 1.0.0 和三个示例。环境准备见 [开始使用](../START-HERE.md)，接口见 [API 参考](api.md)，版本边界见 [兼容说明](versions.md)。

## 保留一份能够运行的原始示例

先用支持的控制台、固件和平台运行原始示例，确认一次真实实体触发到达日志。

随后复制示例目录，再修改自己的副本。这样可以在排查问题时分辨原始示例是否正常，避免把环境问题和自己的改动混在一起。

## 扩展目录包含什么

当前扩展模型使用 `boring-extension.json` 描述身份、入口和声明的能力，Python 文件实现动作逻辑。具体格式见 [扩展接口](extensions.md) 和已发布示例。

示例名字改成自己的名字时，也需要使用自己的扩展 ID。控制台按 ID 区分扩展，不能依靠显示名称区别两个相同 ID 的包。

修改时保留适用的许可及第三方声明。本次采用 PolyForm Noncommercial 1.0.0，参见 [使用许可](../LICENSING.md)。

## 从一个小动作开始

先确定“收到什么触发、执行什么动作、成功结果在哪里可见”。第一次修改可以只改变日志内容，确认修改版被运行，再加入自己的逻辑。

有多种失败原因时，日志应指出实际停在哪一步，例如“没有收到触发”“动作已接受但文件未写入”，不要只打印“失败”。公开日志或截图前移除私有正文和凭据。

## 导入后的副本与开发目录不同

当前控制台导入扩展时会复制文件到受管目录。修改原始开发目录，不代表已经导入的副本自动更新。

调试修改版时，应按对应版本的替换或重新导入说明操作。若版本没有更新入口，需要先停用并移除旧导入项，再导入新的目录；移除可能影响原绑定，应记下绑定并按需重新设置。具体替换方式以已发布控制台说明为准。

仅“重启扩展”不等于重新读取原始开发目录中的修改。

## 验证自己的改动

验证应围绕改动本身。例如修改一个绑定动作，就用真实设备触发它，确认预期结果与日志一致；停用后确认控制台恢复该槽位应有的行为。

手动调用逻辑成功不能替代实体绑定验证。扩展显示运行中，也不能替代动作完成的结果。

映射提案类扩展需要区分“提案已提交”“已批准到草稿”和“设备已写入”，不要把其中一个阶段当成后面的阶段完成。

## 分享自己的作品

按本次许可允许的范围分享修改。说明用途、扩展版本、所用控制台和固件、实际验证的平台，以及已知限制。不要把社区扩展标成官方认证。

如果希望贡献回本仓库，参见 [贡献指南](../CONTRIBUTING.md)。

## 构建 SDK 与开发包

在已经安装开发依赖的虚拟环境中，从仓库或完整开发包根目录执行：

```bash
python -m pip wheel --no-deps --wheel-dir dist ./sdk/python
python tools/build_release.py --output dist
```

第一条构建 SDK wheel；第二条生成三个独立扩展 ZIP，并把文档、源码、协议和扩展 ZIP 汇总到完整开发包。构建工具不依赖私有项目或 Git 历史，也不连接设备或上传 GitHub。

发布产物位于 dist，许可与 NOTICE 会随 SDK 和每个扩展保留。
