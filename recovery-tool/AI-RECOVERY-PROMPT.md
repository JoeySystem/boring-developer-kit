# DMG 无法恢复时，把这段交给 AI

适用于 Codex、Claude Code 等能读取本地文件、运行命令的开发工具。普通聊天网页只能给指导，不能直接操作你的 USB 设备。

先下载本次 Release 的 `recovery-tool-source.zip` 并解压，在该目录启动 AI。也可以克隆仓库后打开 `recovery-tool/`。如有“保存诊断信息”下载的 JSON，一并交给 AI；公开发 Issue 前检查其中的设备序列号和本机路径。

下面整段可以直接复制。不知道的项写“未知”，不要为了填信息反复刷机。

```text
请帮我实际排查并恢复 BORING MIST，而不是只给通用建议。

我的情况：
- Mac 芯片/系统版本：〔填写或由你读取〕
- 当前表现：〔例如左上角灯一直闪、屏幕不亮〕
- DMG 工具表现或报错：〔填写〕
- Boring Console 版本：〔例如官方 0.2.1〕
- 我是否修改过固件：〔是/否/未知，简述〕
- 诊断 JSON 路径：〔有则填写，无则写没有〕

当前目录是 BORING MIST 恢复工具源码。我授权你在本机读取恢复所需的信息、修改此工具并运行验证；在唯一目标设备明确、内置官方固件签名和硬件匹配通过后，通过 USB 执行恢复。不要操作其他设备。

目标是恢复到随工具附带的、有效官方签名的固件，并让官方 Console 正确识别。保留我的按键配置和设备身份。用户不能拆机或接触 BOOT，不要把按 BOOT 当作操作步骤。

请先读 README.md、AGENTS.md、TROUBLESHOOTING.md 和 provisioner/official_recovery.py，再结合实际报错行动：

1. 分清是 macOS 无法打开 DMG/.app、工具依赖缺失、USB 没被识别、端口占用，还是设备的 HELLO/更新协议不响应。检查机器架构和系统版本、已有日志、串口列表及占用者。不要把“只有灯闪”直接归因于没电、操作失误或固件坏了。
2. 如果只是 DMG 无法运行，优先在隔离的 Python 虚拟环境按 README 启动同一源码，不要要求关闭系统安全保护。缺少依赖就安装 requirements.txt，避免更改全局 Python。
3. 如果端口被 Console 等程序占用，提示我退出对应程序；不要杀掉无关进程。完全没找到 USB 时，指导我用数据线直连、换线或换接口，重新观察结果。没有协议响应时，明确告诉我：修改电脑端工具不一定能救回这台设备，不能凭空绕过不可用的设备通道。
4. 只有日志/调用链显示具体问题时才改代码，例如错误的串口选择、解析问题、某一步确实不足的等待时间。做最小修改，为该失败补一个有意义的测试。不要无依据增大所有超时、死循环重试、关闭版本/硬件/签名校验，或把失败改成成功。修改后运行相关测试，再使用工具验证。
5. 固件优先使用 releases/recovery 中原有官方签名镜像。不要改它的二进制、build_id、manifest 或信任公钥，不要生成一个新密钥冒充官方签名。不得擦除整片 Flash、改分区、覆盖身份/NVS、写 eFuse 或尝试生产签发。若确实需要修改固件，先解释具体原因，并明确自改构建不再是原官方固件；本轮先不要擅自走这条路线。
6. 刷写前确认只有一台目标设备，核对硬件和升级能力。使用现有刷写流程，保留断线后按设备序列号重连、精确版本/目标分区/回滚状态验证。传输进度 100% 不是恢复成功。
7. 只有设备成功重启并回读对应 build_id 后，才通过现有 register_with_console 写入已验签的官方发布记录。登记失败应单独报告，不能伪造设备身份或更换 Console 的公钥。请让我用同一 Mac 账户退出工具并重开官方 Console，确认“官方固件”、USB 已连接、设备已认证，并确认屏幕、普通按键和旋钮。
8. 最后用短句说明：实际原因或尚未确认的原因、修改了哪些文件、测试结果、设备是否真的恢复、官方识别是否完成、还需要我做什么。保留诊断记录。如果无可用 USB 通道，请明确停止并建议联系 BORING 售后，不要让我无限重复刷写。

请不要假设客户故障机已经被复现。仅源码测试通过、端口出现或电脑端显示已连接，都不能代替实际恢复和官方识别验证。
```

如果正在使用的 AI 没有终端/文件权限，可以补充：“请一次给我一个可执行步骤，先看真实结果再继续；不要一次发一堆无法判断是否适用的命令。”
